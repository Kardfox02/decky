# VALIDATION.md

**Статус:** план v0.2 · **Цель:** выявлять структурные, технические, визуальные и интерактивные ошибки HTML-дек до передачи аудитории.

Документ описывает желаемую проверку, а не утверждает, что все перечисленные проверки уже реализованы. Источники требований: `DECK_CONTRACT.md` (обязательное) и `DESIGN_GUIDELINES.md` (рекомендации). Проверка рекомендации обязательна в составе V2/V3, но её нарушение классифицируется как MINOR или INFO, если только то же самое не нарушает обязательное требование контракта.

## 1. Уровни проверок

| Уровень | Метод | Статус приёмки |
|---|---|---|
| V0 — структура | JSON, директории, пути, расширения, фон | **Обязателен**, блокирует релиз |
| V1 — статический HTML | базовые метатеги, наличие CSS-основы, локальные ссылки | Блокирует явные ошибки; эвристики — предупреждения |
| V2 — браузерный рендер | 1920 × 1080 и 1280 × 720 в движке плеера, скриншоты, ошибки консоли, ресурсы | **Обязателен** для генерируемых дек |
| V3 — UX и интерактив | клики, варианты тестов, возврат, клавиши | Обязателен для интерактивных слайдов |
| V4 — визуальная ревизия | читаемость и композиция, эксперт/AI + скриншоты | Обязательная человеческая/редакторская оценка перед показом аудитории |

## 2. V0 — валидация `deck.json`

Проверить:

- Наличие `deck/<id>/deck.json`, правильное имя `<id>`.
- `deck_root.resolve()` и `deck_dir.resolve()`; дека не покидает корень через symlink.
- Декодирование UTF-8-sig; корневой JSON — объект.
- `title` — строка и `title.strip()` непустой.
- `slides` — непустой массив объектов.
- `slides[].file` — непустой относительный POSIX-путь, без `\`, `:`, NUL, пустых сегментов, сегментов `.`/`..`, без выхода за деку; существующий файл с `.html` (регистр расширения игнорируется); дубли `file` разрешены.
- Проверить коллизии путей, различающихся только регистром, при переносе на Windows.
- `slides[].background` соответствует `#[0-9A-Fa-f]{6}`.
- Неизвестные ключи корня и объектов слайдов: **игнорируются**; тестируетcя отсутствие ошибки при дополнительных свойствах. Автор не должен полагаться на их обработку.
- Для уникального URL корректно кодировать путь через `quote(..., safe='/')`.

**Негативные тесты:** отсутствует JSON; некорректный JSON; `slides=[]`; пустой title; `background='#fff'`; абсолютный путь; `../escape.html`; `slides/./01.html`; Windows-разделитель; файл не существует; `file='.png'`; symlink наружу; имя папки `my deck`; `a//b.html`; `a/`; `C:/slides/a.html`; `a:b.html`; NUL; коллизии `A.html` и `a.html`. Отдельно подтвердить, что дополнительные свойства игнорируются, а дубли `file` разрешены.

## 3. V1 — HTML и офлайн-ресурсы

Для каждого файла:

- Проверить наличие HTML-документа, `charset="utf-8"`, языка `lang="ru"` для русскоязычной деки (язык — рекомендация).
- Проверить, что `html`/`body` охватывают viewport. Статический анализ CSS здесь лишь предварительный; истинная геометрия проверяется браузером.
- Выявлять как ошибки корневые ссылки (`/assets/...`), протокол-относительные ссылки (`//...`), `<base>` и все обнаружимые внешние URL в `script[src]`, `link[href]`, `img[src]`, CSS `url(...)`, `fetch(...)` и `import`. JS-динамические URL статически не выявляются надёжно; запросы, возникающие в выполненных сценариях, проверяются в V2/V3.
- Проверить, что локальные файлы имеются, пути не выходят за деку.
- Проверить шрифты: системный стек или локальный `.woff2`; внешних шрифтов и CDN нет; для локального шрифта проверить `@font-face`, относительный URL и наличие кириллицы.
- Если используется `assets/theme.css`, проверить относительную ссылку и отсутствие `<base>`/корневых URL.
- `<meta name="viewport">` не требуется; его наличие не считается ошибкой, но и не влияет на viewport.
- Спайк MIME по реальному серверу и `pywebview`: `.html`, `.js`, `.mjs`, `.css`, `.svg`, `.woff2`, `.wasm`; фиксировать Content-Type и факт успешной загрузки, отдельно проверить ES-модули и WebAssembly.
- Пробовать парсить JS и CSS с подходящими инструментами (если они доступны), но не принимать успешный парсинг за гарантию работы.

**Ошибки:** отсутствующий локальный скрипт/стиль/изображение, обнаружимый внешний ресурс или CDN, внешний шрифт.

## 4. V2 — браузерный рендер

Рендерить каждый слайд в **движке плеера** (WebView2 на Windows, WebKit на macOS/Linux), а не только в headless Chromium. Дополнительно делать скриншоты в 1920 × 1080 и 1280 × 720.

Проверить:

- отсутствие ошибок консоли и неуспешных запросов ресурсов;
- геометрию: `scrollWidth`/`scrollHeight` не превышают `clientWidth`/`clientHeight` у `body` и ключевых блоков;
- фон: базовый цвет `body` близок к `background` слайда; если используется градиент или прозрачность — зафиксировать предупреждение и проверить вручную, а не считать это автоматическим провалом;
- фактический `font-family` и отсутствие внешних шрифтовых запросов;
- размеры целей клика: ориентир не меньше 64 × 64 CSS px (рекомендация; меньшее значение само по себе — MINOR);
- бюджет анимации: ориентир — первый полезный кадр не позже ~1 с и общая длительность не дольше 3–4 с (рекомендация); проверить режим `prefers-reduced-motion`;
- отсутствие наложений и обрезки значимого контента, соблюдение безопасной области ≥64 px (скриншоты + визуальная проверка).

```javascript
const report = await page.evaluate(() => {
  const root = document.documentElement;
  const body = document.body;
  const overflow = {
    x: Math.max(root.scrollWidth, body.scrollWidth) > 1920,
    y: Math.max(root.scrollHeight, body.scrollHeight) > 1080
  };
  const outside = [...document.querySelectorAll('[data-validate="content"]')]
    .map(el => ({ el, rect: el.getBoundingClientRect() }))
    .filter(({ rect }) => rect.left < 64 || rect.top < 64 ||
      rect.right > 1920 - 64 || rect.bottom > 1080 - 64)
    .map(({ el }) => el.tagName + (el.id ? '#' + el.id : ''));
  return { overflow, outside };
});
```

**Важно:** порог 64 px в примере соответствует безопасной области; для проверки только границ viewport используйте 0/1920/1080. `scrollWidth`/`scrollHeight` не выявляют наложения и перекрытия. Геометрия по маркеру `data-validate="content"` — добровольное улучшение тестируемости, **не поле JSON и не обязательство плеера**. Без такой маркировки инструменты могут использовать эвристический набор значимых элементов.

## 5. V3 — интерактивность и клавиатура

### Для каждого интерактивного слайда

- Загрузить отдельно: стартовое состояние корректно.
- Провести обычный пользовательский сценарий: выбрать/изменить/проверить результат.
- Проверить минимум один неверный и один верный вариант, если предусмотрены варианты ответа.
- Если есть «Сбросить/Повторить», проверить возврат в исходное состояние.
- Перейти на следующий слайд и обратно: всё корректно перезапускается и не зависит от предыдущего DOM.
- Проверить пошаговое раскрытие: предпочтительно отдельными слайдами; если шаги внутри слайда — локальная кнопка сброса и корректный сброс после возврата.
- Проверить `Tab`/`Enter`/`Space`, видимый фокус и ориентир 64 × 64 CSS px для целей клика; доступность с клавиатуры и размер цели — рекомендации, если нет отдельного обязательного требования контракта.
- Убедиться, что основной сценарий не зависит от автозапуска аудио/видео и `requestFullscreen()`.
- Проверить, что стрелки переключают слайды, когда фокус не в исключённом элементе; если слайд намеренно обрабатывает их, то `preventDefault()` применяется локально.

### Для плеера отдельно

- Не принимать навигационные события во время перехода.
- Проверить последовательность fade-out → фон → src → load → fade-in.
- Проверить принятые в `ARCH.md` тайм-ауты: около 5 с для `HEAD` и около 8 с для `iframe load`. Смоделировать отсутствие HTML *до* `HEAD` (ожидается штатная ошибка). Сценарий удаления между `HEAD`/`GET` — известное негарантированное поведение, пока нет специального детектора HTTP-ошибок.
- Проверить режим `prefers-reduced-motion`.
- Не объявлять сценарий гонки `HEAD`→`GET` покрытым штатным экраном ошибки без отдельной реализованной проверки HTTP-статуса.

## 6. V4 — визуальная и содержательная приёмка

Вопросы на каждый слайд:

- Понятна ли главная мысль за 3–5 секунд?
- Шрифт читается на экране 1280 × 720 и с задних рядов?
- Есть ли осмысленная визуальная иерархия, нет ли случайной пустоты?
- Иллюстрация соответствует смыслу объяснения?
- Код запускается, а ожидаемый результат правильный?
- Есть ли переход от простой аналогии к коду и к самостоятельной задаче?
- Не используются ли непояснённые термины/конструкции для возраста аудитории?
- Можно ли объяснить слайд, не прибегая к незапланированным материалам?

## 7. Классы проблем

| Уровень | Пример | Действие |
|---|---|---|
| **BLOCKER** | Невалидный JSON; путь наружу; отсутствующий HTML; JS падает и ломает задачу | Не выдавать деку |
| **MAJOR** | Текст обрезан; код неверен; критический офлайн-ресурс отсутствует; кнопка не работает | Исправить до показа |
| **MINOR** | Неидеальный перенос; лишняя пустота; слабая композиция на одном слайде | Исправить по возможности |
| **INFO** | Предложение улучшить композицию/подпись | На усмотрение автора |

## 8. Формат отчёта валидатора (вне контракта деки)

Отчёт можно хранить **снаружи** папки деки (например, в артефактах CI). Это **не `deck.json` и не поле деки**.

```json
{
  "deck": "example-deck",
  "status": "failed",
  "issues": [
    {
      "severity": "MAJOR",
      "slide": "slides/04.html",
      "rule": "CONTENT_OVERFLOW",
      "message": "Значимый текст выходит за правую границу"
    }
  ],
  "screenshots": ["screenshots/04.png"]
}
```

## 10. Границы автоматизации

- Не обещать автоматического выявления **всех** наложений, контрастных проблем и визуальных дефектов.
- `scrollWidth`/`scrollHeight` не выявляют наложения и перекрытия.
- Проверка фона при градиенте или прозрачности `body` — предупреждение и ручная проверка, а не автоматический BLOCKER.
- Не путать событие `load` с гарантией HTTP 200 или успешного выполнения кода.
- Не считать Playwright идеальной имитацией `pywebview`; итоговый smoke-test нужен в реальном плеере.
- Не создавать фиктивный статус `passed`, если браузерные или интерактивные проверки фактически не запускались. Использовать `not_run`/`manual_review_required`.
- Не добавлять тестовые поля в `deck.json` ради отчётности.
